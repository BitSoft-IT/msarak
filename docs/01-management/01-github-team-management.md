# دليل إدارة الفريق والعمل في GitHub

**المشروع:** مسارك — منصة التوجيه الأكاديمي والمهني لطلاب الثانوية  
**الحالة:** معتمد للتنفيذ  
**آخر تحديث:** 2026-09-11

## 1. الهدف

هذا الدليل هو المرجع العملي لإدارة المهام والكود والتواصل في GitHub. الهدف أن يعرف كل عضو:

- ما المهمة المطلوبة منه.
- متى يبدأ العمل.
- أين يكتب التحديثات والأسئلة.
- كيف ينشئ فرعه ويرفع عمله.
- كيف يطلب المراجعة.
- متى تُعد المهمة مكتملة.

القاعدة الأساسية: **كل تغيير يبدأ من Issue وينتهي بدمج Pull Request في `main`.**

---

## 2. بنية العمل المعتمدة

| العنصر | استخدامه |
|---|---|
| مستودع واحد | يحتوي على كود المشروع ووثائقه. |
| `main` | الفرع المستقر والمحمي، ولا يُكتب عليه مباشرة. |
| فرع مؤقت لكل Issue | مكان تنفيذ المهمة فقط، ويُحذف بعد الدمج. |
| GitHub Issues | المصدر الرسمي للمهام والمتطلبات والملاحظات. |
| GitHub Project | لوحة متابعة جميع المهام وحالاتها. |
| Pull Requests | مراجعة التغييرات والموافقة عليها قبل الدمج. |
| ملفات التوثيق | المرجع الدائم للقرارات وطريقة تشغيل المشروع. |

لا يوجد فرع `develop`. جميع الفروع المؤقتة تبدأ من `main` وتُدمج إليه بعد المراجعة.

---

## 3. الصلاحيات والمسؤوليات

| العضو | صلاحية GitHub | مسؤوليته في الإدارة |
|---|---|---|
| حارث | Admin أو Maintain | إعداد المستودع، ترتيب الأولويات، حماية `main`، اعتماد الجاهزية، وإجراء الدمج. |
| مالك | Write | تنفيذ مهامه، مراجعة أعمال الخلفية، وتحديث حالاتها. |
| أيمن | Write | تنفيذ مهامه، مراجعة أعمال الواجهة، وتحديث حالاتها. |
| عبدالله حمود | Write | تنفيذ مهام البيانات والاختبار ومراجعتها ضمن تخصصه. |
| ملاطف | Write | تنفيذ مهام المحتوى وتجربة المستخدم ومراجعتها ضمن تخصصه. |

قواعد الصلاحيات:

- لا يدفع أي عضو تغييرات مباشرة إلى `main`.
- لا يدمج صاحب المهمة Pull Request الخاص به.
- حارث ينفذ الدمج بعد تحقق شروطه، ولا يعني ذلك أنه يراجع وحده كل التخصصات.
- يراجع العمل عضو يفهم المجال المتأثر بالتغيير.

## 4. حالات المهام في GitHub Project

| الحالة | معناها | من ينقل المهمة إليها؟ |
|---|---|---|
| `Backlog` | مهمة معروفة لكنها ليست جاهزة للبدء الآن. | حارث |
| `Ready` | الوصف والاعتماد ومعايير القبول واضحة ويمكن بدء المهمة. | حارث |
| `In Progress` | بدأ العضو تنفيذ المهمة فعليًا. | صاحب المهمة |
| `In Review` | فُتح Pull Request وأصبحت المهمة قيد المراجعة. | صاحب المهمة |
| `Done` | تم دمج Pull Request وأُغلقت المهمة. | تلقائيًا أو حارث |

المسار الطبيعي:

`Backlog → Ready → In Progress → In Review → Done`

إذا تعطل العمل، تضاف علامة `blocked` مع تعليق يوضح السبب وما المطلوب ومن الشخص القادر على حله. تبقى المهمة في حالتها الحالية حتى يزول العائق.

يجوز إسناد خمس Issues لكل عضو، لكن يعمل العضو عادةً على **Issue واحدة فقط في حالة `In Progress`** حتى لا تتشتت الأعمال.

---

## 5. متى تصبح المهمة جاهزة للبدء؟

لا تنتقل Issue إلى `Ready` إلا إذا احتوت على:

- هدف واضح.
- نطاق العمل المطلوب.
- ما لا يدخل ضمن المهمة، عند احتمال الالتباس.
- الاعتمادات على المهام الأخرى.
- معايير قبول قابلة للتحقق.
- الملفات أو أجزاء النظام المتوقع تعديلها.
- اسم المسؤول عن التنفيذ.
- اسم المراجع المتوقع.

إذا نقصت معلومة تمنع التنفيذ الصحيح، تُستكمل قبل بدء العمل.

---

## 6. قالب Issue المعتمد

```markdown
## الهدف
صف النتيجة المطلوبة من المهمة باختصار.

## نطاق العمل
- العمل المطلوب الأول.
- العمل المطلوب الثاني.

## خارج النطاق
- شيء مرتبط لكنه غير مطلوب في هذه المهمة.

## الاعتمادات
- تعتمد على #رقم-المهمة، أو: لا يوجد.

## الملفات أو الأجزاء المتوقعة
- المسار أو الجزء المتوقع تعديله.

## معايير القبول
- [ ] معيار واضح يمكن اختباره.
- [ ] معيار واضح يمكن اختباره.
- [ ] تم تحديث التوثيق أو سجل الأوامر عند الحاجة.

## التحقق المطلوب
- الاختبار أو الفحص المطلوب قبل فتح Pull Request.

## المسؤولون
- المنفذ: @username
- المراجع: @username
```

أي عمل جديد ظهر أثناء التنفيذ وله هدف مستقل يُنشأ له Issue جديدة، ولا يُضاف بصمت إلى نطاق المهمة الحالية.

---

## 7. التصنيفات والمراحل الزمنية

### التصنيفات الأساسية

| المجموعة | القيم المستخدمة |
|---|---|
| النوع | `type:feature`، `type:fix`، `type:test`، `type:docs`، `type:refactor` |
| المجال | `area:backend`، `area:frontend`، `area:data`، `area:content`، `area:integration` |
| الأولوية | `priority:high`، `priority:medium`، `priority:low` |
| العوائق | `blocked` |

تكفي عادةً ثلاثة تصنيفات للمهمة: النوع، المجال، والأولوية. تضاف `blocked` عند الحاجة فقط.

### Milestones

تُنشأ خمسة Milestones مطابقة لدفعات خطة العمل:

1. الدفعة الأولى: التأسيس والعقود.
2. الدفعة الثانية: القلب الوظيفي.
3. الدفعة الثالثة: التكامل.
4. الدفعة الرابعة: التحقق والتحسين.
5. الدفعة الخامسة: الإغلاق والتسليم.

---

## 8. بدء تنفيذ المهمة

بعد انتقال Issue إلى `Ready`:

1. يتأكد العضو أنه المسؤول عنها وأن اعتمادها السابق مكتمل.
2. ينقلها إلى `In Progress`.
3. يحدّث نسخته من `main`.
4. ينشئ فرعًا مؤقتًا مرتبطًا برقم Issue.

```bash
git switch main
git pull origin main
git switch -c feature/12-assessment-session
git push -u origin feature/12-assessment-session
```

### أسماء الفروع

| نوع العمل | الصيغة | مثال |
|---|---|---|
| ميزة | `feature/<issue>-<short-name>` | `feature/12-assessment-session` |
| إصلاح | `fix/<issue>-<short-name>` | `fix/31-score-calculation` |
| اختبار | `test/<issue>-<short-name>` | `test/19-assessment-flow` |
| توثيق | `docs/<issue>-<short-name>` | `docs/22-setup-guide` |
| إعادة تنظيم | `refactor/<issue>-<short-name>` | `refactor/24-result-service` |

يُستخدم رقم Issue، وأحرف إنجليزية صغيرة، وشرطات بدل المسافات.

---

## 9. أثناء التنفيذ

- يلتزم العضو بنطاق Issue ولا يجمع مهام مستقلة في الفرع نفسه.
- يرفع عمله دوريًا إلى الفرع المؤقت حتى لا يبقى محليًا فقط.
- يسجل السؤال أو العائق داخل Issue بدل أن يبقى في محادثة خاصة.
- لا يضع كلمات مرور أو مفاتيح أو محتوى ملف `.env` في GitHub.
- يحدّث ملف التوثيق المتأثر عند تغيير طريقة التشغيل أو السلوك.
- يوثق أوامر الإعداد أو التشغيل الجديدة في `docs/commands/` باسم مرتبط بالمهمة، مثل `issue-12.md`.

ملف سجل الأوامر يتضمن فقط:

````markdown
# Issue #12 — سجل التنفيذ

## الأوامر المستخدمة
```bash
php artisan make:controller AssessmentController
php artisan test
```

## الغرض
- إنشاء المتحكم الخاص بالتقييم.
- تشغيل الاختبارات بعد التغيير.

## ملاحظات
- لا توجد خطوات يدوية إضافية.
````

لا يُسجل كل أمر تنقل عادي، بل الأوامر التي يحتاجها عضو آخر لفهم التغيير أو تكراره.

---

## 10. كتابة Commits

الصيغة:

```text
<type>: <clear short description>
```

الأنواع المستخدمة: `feat`، `fix`، `test`، `docs`، `refactor`، `chore`.

أمثلة:

```text
feat: persist assessment answers in session
fix: prevent incomplete assessment submission
test: cover riasec score calculation
docs: document assessment setup commands
```

كل Commit يمثل تغييرًا مترابطًا يمكن فهمه، ولا يُشترط تقسيم التغيير الصغير بصورة مصطنعة.

---

## 11. فتح Pull Request

يفتح العضو Pull Request عندما:

- يكتمل نطاق Issue.
- تتحقق معايير القبول.
- تنجح الاختبارات والفحوص المحلية المناسبة.
- يُحدّث التوثيق وسجل الأوامر عند الحاجة.
- يُرفع الفرع إلى GitHub.

يكون دائمًا:

- `base`: الفرع `main`.
- `compare`: فرع المهمة المؤقت.

### قالب Pull Request

```markdown
## الملخص
ما الذي تم إنجازه؟

## سبب التغيير
لماذا احتاج المشروع هذا التغيير؟

## المهمة المرتبطة
Closes #رقم-المهمة

## التغييرات
- التغيير الأول.
- التغيير الثاني.

## التحقق والاختبارات
- [ ] شُغلت الاختبارات المناسبة بنجاح.
- [ ] تم فحص السلوك يدويًا عند الحاجة.
- [ ] تم تحديث التوثيق أو سجل الأوامر عند الحاجة.
- [ ] لا توجد أسرار أو ملفات محلية ضمن التغييرات.

## تعليمات التشغيل
- أمر migration أو build أو خطوة إضافية، أو: لا يوجد.

## لقطات الواجهة
- تضاف عند وجود تغيير مرئي، أو: لا ينطبق.
```

بعد فتحه، ينقل صاحب المهمة Issue إلى `In Review` ويطلب المراجع المحدد.

---

## 12. اختيار المراجع

| نوع التغيير | المراجع الأساسي | مراجعة إضافية عند الحاجة |
|---|---|---|
| Backend، Sessions، RIASEC | مالك أو حارث | عبدالله عند تأثير البيانات والاختبارات. |
| قاعدة البيانات وMigrations | عبدالله حمود أو مالك | حارث عند تغيير معماري. |
| Blade وTailwind وJavaScript | أيمن | مالك عند تغيير عقد البيانات مع الخلفية. |
| الاختبارات والبيانات التجريبية | عبدالله حمود | مالك للمنطق أو ملاطف للمحتوى. |
| التخصصات والمحتوى والأسئلة والنتائج | ملاطف | عبدالله للبيانات أو أيمن لطريقة العرض. |
| التكامل والإعداد والتوثيق العام | حارث | صاحب التخصص المتأثر. |
| عمل حارث نفسه | صاحب التخصص المتأثر | مراجع ثانٍ فقط إن كان التغيير حساسًا. |

تكفي موافقة مؤهلة واحدة في العمل المعتاد. تُطلب مراجعة ثانية فقط عندما يمس التغيير أكثر من مجال مهم، أو يغير قاعدة البيانات أو معادلة RIASEC أو قرارًا معماريًا.

المراجع يختار نتيجة واضحة:

- `Approve`: التغيير جاهز.
- `Request changes`: يوجد تعديل يمنع الدمج.
- `Comment`: سؤال أو اقتراح غير مانع.

تُحل جميع الملاحظات المانعة قبل الدمج. لا يلزم اجتماع؛ المناقشة والقرار يُسجلان في Pull Request.

---

## 13. شروط الدمج

لا يدمج حارث Pull Request إلا بعد تحقق الآتي:

- مرتبط بـ Issue صحيحة باستخدام `Closes #...`.
- نطاق المهمة ومعايير قبولها مكتملة.
- حصل على الموافقة المطلوبة.
- لا توجد ملاحظات مانعة غير محلولة.
- الاختبارات والفحوص الآلية المطلوبة ناجحة.
- لا توجد تعارضات مع `main`.
- التوثيق وسجل الأوامر محدثان عند الحاجة.
- لا يحتوي التغيير على أسرار أو ملفات غير مطلوبة.

طريقة الدمج المعتمدة: **Squash and merge**. بعد الدمج يُحذف الفرع المؤقت، وتُغلق Issue، وتنتقل إلى `Done`.

---

## 14. معالجة التعارضات

إذا تغيّر `main` وظهر تعارض، يصلح صاحب الفرع التعارض داخل فرعه:

```bash
git switch feature/12-assessment-session
git fetch origin
git merge origin/main
```

ثم:

1. يحل الملفات المتعارضة بعناية.
2. يشغل الاختبارات المناسبة.
3. يسجل التغيير ويرفع الفرع نفسه.
4. يطلب إعادة المراجعة إذا تغير جزء جوهري.

لا يُحل التعارض بتعديل مباشر على `main`.

---

## 15. إعدادات المستودع المطلوبة

يضبط حارث Branch protection rule أو Repository ruleset على `main` بحيث:

- يُمنع الدمج دون Pull Request.
- تُطلب موافقة مراجع واحد على الأقل.
- تُطلب معالجة المحادثات المانعة قبل الدمج.
- تُطلب نجاح فحوص CI بعد إضافتها للمشروع.
- لا يملك أعضاء الفريق مسارًا اعتياديًا للدفع المباشر إلى `main`.

كما يضبط المستودع على:

- السماح بـ `Squash merging` واعتماده للفريق.
- حذف فرع Pull Request تلقائيًا بعد الدمج.
- تفعيل قالب Issue وقالب Pull Request.
- ربط Issues بلوحة GitHub Project.

إذا لم يوفّر نوع الحساب أو خطة GitHub إعداد حماية معينًا، يطبق الفريق القاعدة نفسها إجرائيًا، ويتولى حارث وحده الدمج إلى `main`.

---

## 16. أتمتة لوحة المشروع

تُستخدم الأتمتة البسيطة فقط:

- عند إضافة Issue إلى المشروع: `Backlog`.
- عند فتح Pull Request مرتبط: `In Review`.
- عند دمج Pull Request وإغلاق Issue: `Done`.

تبقى عمليتا `Ready` و`In Progress` يدويتين لأنهما تعبران عن قرار الجاهزية وبدء العمل الفعلي.

---

## 17. التواصل دون اجتماعات إلزامية

- تفاصيل المهمة وأسئلتها داخل Issue.
- النقاش حول الكود داخل Pull Request.
- القرار التقني الدائم يُضاف إلى ملف القرارات التقنية.
- يستخدم `@mention` فقط للشخص المطلوب منه إجراء واضح.
- عند وجود عائق، يكتب العضو: السبب، أثره، وما الذي يحتاجه، ثم يضع `blocked`.
- القرار المهم لا يبقى في رسالة خاصة؛ تُنقل خلاصته إلى Issue أو الوثيقة المناسبة.

---

## 18. قائمة العضو اليومية

1. افتح GitHub Project واعرف المهمة الحالية.
2. لا تبدأ إلا مهمة في `Ready` ومسندة إليك.
3. انقلها إلى `In Progress` وأنشئ فرعها من أحدث `main`.
4. نفذ النطاق فقط، واكتب Commits واضحة.
5. اختبر عملك وحدّث التوثيق المطلوب.
6. افتح Pull Request واربط Issue واطلب المراجع.
7. عالج الملاحظات ثم انتظر الدمج.
8. بعد الدمج، حدّث نسختك من `main` وابدأ المهمة التالية الجاهزة.

## 19. قائمة حارث لإدارة الفريق

1. يرتب Issues حسب الاعتمادات والأولوية.
2. ينقل المهمة إلى `Ready` بعد اكتمال معلوماتها واعتمادها السابق.
3. يتأكد أن لكل مهمة منفذًا ومراجعًا واضحين.
4. يتابع `blocked` ويحدد المطلوب لحل العائق.
5. يراجع بوابة الدمج ولا يتجاوز الاختبارات أو المراجعة.
6. يدمج بطريقة Squash ويحذف الفرع المؤقت.
7. يتأكد من انتقال المهمة إلى `Done` وبدء المهمة التالية الصحيحة.
8. يوثق أي تغيير في التقنية أو النطاق قبل تطبيقه على الفريق.

---

## 20. ممنوعات واضحة

- العمل دون Issue.
- الدفع المباشر إلى `main`.
- بدء مهمة تعتمد على عمل غير مكتمل.
- جمع عدة أهداف مستقلة داخل Pull Request واحد.
- دمج صاحب العمل لنفسه دون مراجعة.
- مشاركة `.env` أو كلمات المرور أو المفاتيح.
- تعديل قرار تقني معتمد دون توثيق القرار الجديد.
- اعتبار المحادثات الخاصة بديلًا عن التوثيق الرسمي.

---

## 21. ترتيب إنشاء GitHub لاحقًا

عند الانتقال إلى التنفيذ الفعلي، يكون الترتيب:

1. إنشاء المستودع ورفع النسخة الأساسية من المشروع إلى `main`.
2. دعوة الأعضاء ومنح الصلاحيات.
3. حماية `main` وضبط الدمج والحذف التلقائي للفروع.
4. إضافة قوالب Issues وPull Requests.
5. إنشاء التصنيفات الخفيفة المذكورة في الدليل.
6. إنشاء GitHub Project وحالاته وأتمتته البسيطة.
7. إنشاء Milestones الخمسة.
8. إنشاء Issues الخمس والعشرين حسب خطة العمل وإسنادها.
9. بدء الدفعة الأولى فقط، ثم فتح الدفعات التالية حسب الاعتمادات.

بهذا النظام تكون كل مهمة قابلة للتتبع من تعريفها إلى دمجها، وتظل إدارة الفريق بسيطة وواضحة دون إضافة طبقات لا يحتاجها المشروع.
