# دليل مراجعة الكود

**المشروع:** مسارك — منصة التوجيه الأكاديمي والمهني لطلاب الثانوية  
**الحالة:** معتمد للتنفيذ  
**آخر تحديث:** 2026-09-11

## 1. الهدف

هذا الدليل يوضح كيف يراجع الفريق كل Pull Request قبل دمجه في `main`، بطريقة خفيفة وواضحة تمنع الأخطاء دون تعطيل العمل.

المراجعة هدفها التأكد من أن التغيير:

- ينفذ Issue المطلوبة فقط.
- يعمل بصورة صحيحة وآمنة.
- لا يكسر أجزاء المشروع الأخرى.
- يمكن فهمه وصيانته.
- يتوافق مع القرارات التقنية والمعمارية المعتمدة.

هذا الدليل يكمل `03-code-management-guide.md`. إدارة Issue والفرع وPull Request والدمج موجودة هناك، أما هنا فالتركيز على **فحص التغيير واتخاذ قرار المراجعة**.

---

## 2. القواعد الأساسية

1. كل Pull Request يحتاج مراجعة مؤهلة قبل الدمج.
2. يراجع المراجع المحدد العمل؛ فإن كان صاحب العمل نفسه أجرى Self-review موثقة (لا يُطلب Approve رسمي لأن GitHub لا يسمح به لصاحب PR)، وإن كان شخصاً آخر راجع ومنح Approve عند الاقتناع.
3. المراجع يُختار حسب مجال التغيير، وليس حسب ترتيب ثابت للأشخاص.
4. تكفي مراجعة المراجع المحدد في التغيير المعتاد (Approve خارجي أو Self-review موثقة).
5. تُطلب مراجعة ثانية فقط للتغييرات الحساسة أو العابرة لأكثر من مجال.
6. الملاحظات تناقش الكود والنتيجة، ولا تقيم الشخص.
7. كل ملاحظة يجب أن تكون واضحة: مانعة، اقتراح، أو سؤال.
8. لا يلزم اجتماع؛ النقاش والقرار يبقيان داخل Pull Request.

---

## 3. توزيع المراجعة حسب المجال

| مجال التغيير | المراجع الأساسي المناسب | مراجعة إضافية عند الحاجة |
|---|---|---|
| Backend، Controllers، Services، Sessions، RIASEC | مالك أو حارث | عبدالله إذا تأثرت البيانات أو الاختبارات. |
| قاعدة البيانات، Migrations، Models، Seeders | عبدالله حمود أو مالك | حارث إذا تغير التصميم المعماري. |
| Blade، Tailwind، JavaScript، تجربة الواجهة | أيمن | مالك إذا تغير عقد البيانات مع Backend. |
| الاختبارات، Fixtures، جودة البيانات | عبدالله حمود | مالك للمنطق أو ملاطف لصحة المحتوى. |
| الأسئلة، التخصصات، تفسير النتائج، النصوص | ملاطف | عبدالله للبيانات أو أيمن لطريقة العرض. |
| التكامل، الإعداد، الأمن العام، الإصدار | حارث | صاحب المجال المتأثر. |
| Pull Request أنشأه حارث | صاحب التخصص المتأثر | مراجع ثانٍ فقط عند حساسية التغيير. |

حارث يتحقق من بوابة الدمج وينفذ الدمج، لكنه لا يحتاج إلى إعادة مراجعة تقنية كاملة بعد مراجعة المراجع المحدد (Approve خارجي أو Self-review موثقة) ما لم يوجد خطر أو تعارض واضح. وإذا كان حارث نفسه هو المنفذ والمراجع المحدد فيجري Self-review ثم يدمج وفق الشروط نفسها.

---

## 4. متى نطلب مراجعًا ثانيًا؟

تُطلب مراجعة ثانية إذا كان التغيير:

- يغير بنية قاعدة البيانات وعقد الواجهة معًا.
- يغير معادلة حساب RIASEC أو تفسير النتيجة.
- يمس المصادقة أو الصلاحيات أو ملكية بيانات المستخدم.
- يغير قرارًا تقنيًا أو معماريًا معتمدًا.
- يجمع محتوى علميًا مع منطق برمجي يؤثر في النتيجة.
- كبيرًا بصورة تجعل تخصص مراجع واحد غير كافٍ.

غير ذلك، لا نضيف مراجعًا ثانيًا لمجرد زيادة الإجراءات.

---

## 5. قبل بدء المراجعة

يتأكد المراجع أولًا من أن Pull Request يحتوي على:

- رابط Issue باستخدام `Closes #...`.
- وصف واضح لما تغير ولماذا.
- نطاق صغير ومترابط.
- معايير قبول يمكن التحقق منها.
- نتيجة الاختبارات التي شغلها المنفذ.
- تعليمات migration أو build أو إعداد، إن وجدت.
- تحديث التوثيق وسجل الأوامر عند الحاجة.
- لقطات شاشة إذا كان هناك تغيير مرئي.

إذا كانت هذه المعلومات ناقصة لدرجة تمنع فهم التغيير، يطلب المراجع استكمالها قبل فحص الكود.

## 6. خطوات المراجعة

### الخطوة 1: فهم المطلوب

- اقرأ Issue ومعايير قبولها.
- اقرأ وصف Pull Request.
- افهم النتيجة المطلوبة قبل قراءة التفاصيل.

### الخطوة 2: فحص نطاق التغيير

- تأكد أن الملفات المعدلة مرتبطة بالمهمة.
- تحقق من عدم إضافة ميزة مستقلة أو إعادة هيكلة غير مطلوبة.
- إذا ظهر عمل مستقل، اطلب نقله إلى Issue منفصلة.

### الخطوة 3: فحص السلوك والمنطق

- هل يحقق التغيير جميع معايير القبول؟
- هل يعالج الحالات الطبيعية والحالات الحدية المتوقعة؟
- هل رسائل الخطأ والسلوك عند الفشل واضحان؟
- هل يعتمد على القرارات التقنية والنماذج المعتمدة؟

### الخطوة 4: فحص جودة الكود

- الأسماء واضحة ومتسقة مع المشروع.
- الدوال والفئات تؤدي مسؤوليات مفهومة.
- لا يوجد تكرار مؤثر أو تعقيد دون حاجة.
- لا يوجد كود ميت أو ملفات مؤقتة أو تعليمات تصحيح منسية.
- كود PHP متوافق مع تنسيق المشروع وPSR-12.
- التعليقات تشرح السبب عند الحاجة، ولا تكرر ما يقوله الكود.

### الخطوة 5: فحص الأمان والخصوصية

- المدخلات تخضع لـ Validation مناسبة.
- المستخدم لا يصل إلى بيانات أو نتائج لا يملكها.
- المسارات الحساسة محمية بالمصادقة والصلاحيات المناسبة.
- مخرجات Blade لا تستخدم عرض HTML غير المفلتر دون سبب آمن.
- لا توجد استعلامات خام غير آمنة أو قيم مدمجة داخل SQL.
- لا توجد كلمات مرور أو مفاتيح أو محتوى `.env` أو بيانات شخصية في Commit.
- لا تُحفظ بيانات حساسة في Session أو السجلات دون حاجة.

### الخطوة 6: فحص البيانات والأداء

- العلاقات والقيود وأنواع الحقول صحيحة.
- Migration قابلة للتنفيذ ولا تفقد بيانات دون قرار واضح.
- لا توجد استعلامات متكررة داخل حلقات بصورة غير ضرورية.
- لا تُحمّل بيانات أكثر مما تحتاجه الصفحة.
- ملفات JSON، ومنها دليل التخصصات، صحيحة البنية وقابلة للقراءة.

### الخطوة 7: فحص الاختبارات

- يوجد اختبار للسلوك المهم الذي أضيف أو تغير.
- تشمل الاختبارات حالة النجاح وحالات الفشل المهمة.
- حساب RIASEC والملكية والصلاحيات تحتاج اختبارات دقيقة عند تأثرها.
- شُغلت الاختبارات الحالية ولم يظهر انحدار واضح.

يمكن للمراجع تشغيل ما يناسب التغيير، مثل:

```bash
php artisan test
```

وعند الحاجة إلى فحص تنسيق PHP، يستخدم أمر التنسيق المعتمد في المشروع إن كان متاحًا.

### الخطوة 8: فحص الواجهة والمحتوى

عند وجود تغيير مرئي أو نصي:

- الواجهة تعمل على المقاسات الأساسية المتفق عليها.
- حالات التحميل والخطأ والبيانات الفارغة واضحة.
- الحقول والأزرار قابلة للاستخدام بلوحة المفاتيح قدر الإمكان.
- النصوص مفهومة ومتسقة لغويًا.
- عرض نتيجة RIASEC لا يقدم حكمًا قطعيًا أو ادعاءً غير معتمد.
- دليل التخصصات يقرأ من المصدر الثابت المعتمد ولا ينشئ قاعدة بيانات مخالفة للقرار.

### الخطوة 9: اتخاذ القرار

بعد إنهاء الفحص، يختار المراجع قرارًا واحدًا واضحًا:

- `Approve` (أو اكتمال Self-review الموثقة عند تطابق المراجع مع المنفذ): جاهز للدمج.
- `Request changes`: توجد مشكلة مانعة يجب إصلاحها.
- `Comment`: توجد أسئلة أو اقتراحات، دون منع الدمج.

## 7. تصنيف ملاحظات المراجعة

يبدأ كل تعليق بواحد من التصنيفات التالية:

| التصنيف | معناه | هل يمنع الدمج؟ |
|---|---|---|
| `Blocking:` | خطأ أو خطر أو نقص لازم للإكمال. | نعم |
| `Suggestion:` | تحسين مفيد لكنه ليس ضروريًا لهذه Issue. | لا |
| `Question:` | طلب توضيح قبل الحكم على الجزء. | حسب الإجابة |

أمثلة:

```text
Blocking: هذا المسار يعرض نتيجة أي مستخدم بالمعرف فقط. يجب التحقق من ملكية النتيجة قبل إرجاعها.
```

```text
Suggestion: يمكن استخراج النص المتكرر إلى Component مستقل لاحقًا؛ هذا لا يمنع دمج المهمة الحالية.
```

```text
Question: هل بقاء الإجابات في Session بعد حفظ النتيجة مقصود؟ وضّح السلوك المعتمد هنا.
```

الملاحظة الجيدة تحدد المكان والمشكلة وسبب أهميتها والنتيجة المطلوبة، ولا تفرض أسلوب تنفيذ واحدًا إذا كانت هناك حلول صحيحة متعددة.

---

## 8. ما الذي يمنع الموافقة؟

يستخدم المراجع `Request changes` عند وجود واحد أو أكثر من الآتي:

- معيار قبول غير منفذ.
- خطأ منطقي أو سلوك غير صحيح.
- ثغرة أمنية أو وصول غير مصرح به.
- احتمال فقد بيانات أو إفسادها.
- اختبار مهم مفقود أو اختبارات فاشلة.
- تعارض مع قرار تقني أو معماري معتمد.
- تغيير خارج نطاق Issue قد يسبب خطرًا أو تعقيدًا.
- كود لا يمكن تشغيله أو مراجعته بسبب نقص تعليمات لازمة.

لا يمنع الدمج بسبب:

- تفضيل شخصي في التسمية مع وجود اسم صحيح وواضح.
- تحسين تجميلي غير مطلوب.
- إعادة هيكلة مستقبلية لا يحتاجها السلوك الحالي.
- اختلاف أسلوب لا يخالف معيار المشروع ولا يضيف خطرًا.

---

## 9. مسؤولية صاحب Pull Request

بعد وصول الملاحظات:

1. يقرأ جميع التعليقات.
2. يصلح كل ملاحظة `Blocking` في الفرع نفسه.
3. يرد على التعليق موضحًا ما تم أو سبب اعتراضه.
4. يشغل الاختبارات المتأثرة من جديد.
5. يرفع التعديلات إلى الفرع نفسه، ولا يفتح Pull Request جديدًا.
6. يطلب إعادة المراجعة.
7. لا يغلق محادثة مانعة قبل تنفيذ الحل أو اتفاق الطرفين عليه.

إذا كان الاعتراض يكشف تغييرًا جديدًا خارج نطاق Issue، ينشأ له Issue مستقلة بدل توسيع العمل بلا ضبط.

---

## 10. مسؤولية المراجع بعد التعديل

عند طلب إعادة المراجعة:

- يفحص التعديلات الجديدة والمناطق المتأثرة بها.
- يتأكد من معالجة الملاحظات المانعة.
- لا يعيد فتح موضوع حُسم إلا إذا ظهر أثر جديد واضح.
- يمنح `Approve` (أو يوثق اكتمال Self-review إن كان هو المنفذ) عندما تصبح بوابة الجودة مكتملة.

إذا تغير Pull Request بصورة جوهرية بعد الموافقة، تُعاد المراجعة قبل الدمج.

---

## 11. بوابة الجودة حسب نوع التغيير

### Backend والمنطق

- Validation واضحة.
- الصلاحيات والملكية صحيحة.
- Controllers غير محملة بمنطق يمكن عزله بوضوح.
- استجابات النجاح والفشل متسقة.
- اختبارات السلوك الأساسي موجودة.

### قاعدة البيانات

- أسماء الجداول والحقول والعلاقات متسقة مع نموذج البيانات.
- المفاتيح والقيود والفهارس اللازمة صحيحة.
- Migration آمنة ومفهومة.
- Seeders وFactories لا تخالف البيانات المعتمدة.

### الواجهة

- تحقق معايير قبول الشاشة.
- حالات الخطأ والفراغ والتحميل موجودة عند الحاجة.
- لا يوجد كسر واضح على الهاتف أو الحاسوب.
- JavaScript لا يكرر منطق الخادم الحساس.
- النصوص والمكونات متسقة.

### الاختبارات

- تختبر النتيجة والسلوك، لا تفاصيل تنفيذ هشة بلا حاجة.
- مستقلة ويمكن تكرارها.
- تغطي الأخطاء المهمة إلى جانب النجاح.
- لا تعتمد على ترتيب تشغيل اختبارات أخرى.

### المحتوى والتخصصات

- المحتوى يطابق المصادر والقرارات المعتمدة.
- الأسئلة الثمانية عشر محفوظة دون تغيير غير معتمد.
- ترميز RIASEC والخيارات صحيحان.
- JSON صالح ومتسق في الحقول.
- تفسير النتيجة واضح وغير مضلل.

---

## 12. متى تعتبر المراجعة مكتملة؟

تُعد المراجعة مكتملة عندما:

- فُحصت Issue والتغييرات المتصلة بها.
- تحققت معايير القبول.
- نجحت الاختبارات والفحوص المطلوبة.
- عولجت جميع الملاحظات المانعة.
- حُلت المحادثات اللازمة.
- حدّث التوثيق وسجل الأوامر عند الحاجة.
- اكتملت مراجعة المراجع المحدد: `Approve` من الخارجي، أو Self-review موثقة من المنفذ عند تطابقهما.

بعدها يتحقق حارث من شروط الدمج المذكورة في `03-code-management-guide.md`، ثم يدمج باستخدام **Squash and merge** ويحذف الفرع المؤقت.

---

## 13. المراجعة عند الاستعجال

الاستعجال لا يلغي المراجعة. عند وجود إصلاح عاجل:

- تُحدد المشكلة والأثر بوضوح في Issue.
- يكون Pull Request صغيرًا ومخصصًا للإصلاح.
- يراجع صاحب التخصص التغيير.
- تشغل الاختبارات الأقرب للمشكلة.
- يوثق أي تحقق مؤجل في Issue لاحقة قبل الدمج.

لا تستخدم صفة «عاجل» لتجاوز الأمان أو الصلاحيات أو سلامة البيانات.

---

## 14. ممنوعات المراجعة

- الموافقة دون فهم الغرض الأساسي للتغيير.
- تحويل كل اقتراح شخصي إلى شرط للدمج.
- كتابة تعليق غامض مثل «عدّل هذا» دون سبب.
- مطالبة صاحب المهمة بعمل خارج نطاقها دون إنشاء Issue جديدة.
- مهاجمة الشخص أو السخرية من مستواه.
- مناقشة قرار مهم خارج GitHub دون تسجيل خلاصته.
- دمج Pull Request فيه ملاحظة مانعة غير محلولة.
- إضافة اجتماعات إلزامية لعملية يمكن حسمها داخل Pull Request.

---

## 15. الخلاصة التنفيذية

### صاحب العمل

`Issue مكتملة → تنفيذ واختبار → Pull Request واضح → معالجة الملاحظات → طلب إعادة المراجعة`

### المراجع

`فهم المطلوب → فحص النطاق والمنطق والأمان والاختبارات → تعليقات مصنفة → قرار واضح`

### حارث

`التحقق من الموافقة والفحوص والتوثيق → Squash and merge → حذف الفرع → Done`

بهذا تبقى المراجعة دقيقة ومفهومة، ويُمنع الخطأ الحقيقي دون زيادة إجراءات لا يحتاجها المشروع.
